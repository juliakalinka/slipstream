# Обслуговування розгорнутої системи

Опис складу служб і самої машини — у [azure/README.md](azure/README.md).
Тут — те, що система робить за розкладом, і що з цим робити людині.

## Завдання за розкладом

| Коли | Що | Одиниця systemd |
|---|---|---|
| щодня 02:30 | резервна копія бази | `slipstream-backup.timer` |
| щодня 03:30 | перенавчання моделей | `slipstream-retrain.timer` |

Копіювання стоїть **раніше** за перенавчання свідомо: якщо перенавчання
чимось зашкодить, стан бази до нього вже збережено.

Обидва таймери мають `Persistent=true`. Машину між демонстраціями зупиняють,
тому пропущений запуск надолужується після вмикання, а не просто втрачається.
Саме через це в обох одиницях є `ExecStartPre=wait_services.sh`: одразу після
вмикання контейнери ще піднімаються.

Встановлення (одноразово):

```bash
sudo cp /opt/slipstream/deploy/systemd/* /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now slipstream-backup.timer slipstream-retrain.timer
systemctl list-timers 'slipstream-*'
```

Подивитися, що відбувалося:

```bash
journalctl -u slipstream-backup.service -u slipstream-retrain.service --since '2 days ago'
```

## Доменне ім'я

Система доступна за іменем **slipstream-ci.duckdns.org**. Ім'я, видане хмарною
платформою, лишається робочим і перенаправляє на основне з кодом 301, тому
раніше видані посилання не ламаються.

Перемикання на інше ім'я виконується одним сценарієм із машини адміністратора:

```bash
./set_domain.sh --dry-run   # показати, що буде зроблено
./set_domain.sh             # створити запис, доставити конфігурацію, перезапустити проксі
```

Передумова — файл `~/.config/duckdns.env` із рядками `DUCKDNS_DOMAIN` і
`DUCKDNS_TOKEN`. Маркер читається лише сценарієм і нікуди не виводиться.

Два місця, де легко зламати доступ назовні, і що з ними зроблено.

**Однакові імена.** Якщо `DOMAIN` і `DOMAIN_LEGACY` збігаються, Caddy вважає
опис неоднозначним і **не запускається взагалі** — тобто система зникає з
мережі цілком. Тому обидві змінні обов'язкові, мають відрізнятися, а опис
перевіряється `caddy validate` **до** перезапуску; за хибного опису сценарій
повертає попередній `.env` і нічого не чіпає.

**Стандартний вхід.** Сценарій надходить на сервер через стандартний вхід, а
`docker compose` без прапорця `-T` цей самий вхід вичитує — і решта сценарію
зникає без жодної помилки. Проявилося це так: `.env` змінився, проксі не
перезапустився, нове ім'я не відповідало. Тому всі виклики `docker compose` у
віддаленій частині мають `-T` і `</dev/null`.

Оновлювача адреси не потрібно: публічна адреса в Azure статична й переживає
зупинку машини.

## Резервні копії

Копіюється **лише база**. Навчені моделі в томі `models_store` не копіюються
свідомо: вони похідні від історії прогонів і відтворюються навчанням, тоді як
сама історія — ні.

```bash
./backup.sh            # зробити копію й прибрати надлишкові
./backup.sh --check    # перевірити найсвіжішу копію ВІДНОВЛЕННЯМ
```

Зберігається сім останніх копій у `/var/backups/slipstream`. Порядок дій у
сценарії має значення: спершу вивантаження в тимчасовий файл, потім перевірка
цілості, і лише потім переміщення й ротація. Інакше обірване вивантаження
витіснило б із ротації справну копію.

`--check` відновлює копію в **окрему** базу `slipstream_restore_check`,
показує кількість рядків у головних таблицях і прибирає її. Робочої бази це
не торкається. Копія, яку ніколи не відновлювали, копією не є, тому перевірку
варто робити хоча б перед кожною демонстрацією.

Відновлення на робочу базу (дані, що є зараз, буде заміщено):

```bash
gzip -dc /var/backups/slipstream/db-РРРРММДД-ГГХХ.sql.gz \
  | docker compose -f docker-compose.prod.yml exec -T db \
    psql -v ON_ERROR_STOP=1 -U "$POSTGRES_USER" -d "$POSTGRES_DB"
docker compose -f docker-compose.prod.yml restart api
```

## Перенавчання моделей

```bash
./retrain.sh                 # усі проєкти, з перевіркою приросту історії
./retrain.sh --force         # незалежно від приросту
./retrain.sh --project 2
```

Сценарій `scripts/retrain_all.py` робить дві речі, яких не робить ендпоінт
перенавчання в інтерфейсі.

**Не навчає без потреби.** Якщо з часу попереднього навчання додалося менше
ніж 20 конвеєрів, проєкт пропускається.

**Не дає тихо погіршити систему.** Реєстр робить кожну нову версію активною
одразу. Для запуску вручну це нормально — людина бачить метрики, — але вночі
нікого немає. Тому після навчання головна метрика порівнюється з попередньою
активною версією (`roc_auc` для ризику й ранжування, `r2` для тривалості), і
при погіршенні понад `--tolerance` система повертається до попередньої версії.
Обидві версії лишаються в реєстрі, тому причину видно в розділі «Моделі».

Це не теоретична обережність: під час першого ж запуску на сервері дві моделі
з чотирьох вийшли гіршими на доданих даних і були повернені.

## Захист входу

Невдалі спроби входу обмежені окремо за адресою джерела (вісім спроб) і за
обліковим записом (двадцять). Вікно обліку й блокування — п'ятнадцять хвилин;
відповідь 429 несе заголовок `Retry-After`. Успішний вхід знімає підозру.

Облік ведеться в пам'яті процесу застосунку, тому **за кількох робочих
процесів** потрібне спільне сховище (Redis). Зараз процес один.

Адреса джерела береться з `X-Forwarded-For` **з кінця** ланцюжка: Caddy додає
туди адресу, з якої запит надійшов до нього, і довіряти можна лише стільком
останнім елементам, скільки власних проксі стоїть перед застосунком
(`TRUSTED_PROXIES=1`). Якби цього не було, обмеження рахувалося б на адресу
проксі, тобто на всіх користувачів разом, і один сторонній замкнув би вхід
усім.
