# Стенд: GitLab CE + Slipstream

Стенд доводить те, чого не може довести жоден розрахунок на історичних даних:
що контур справді замикається. Коміт породжує конвеєр, конвеєр запитує план,
виконує **саме цей** план як дочірній конвеєр, а звіти JUnit повертаються в
систему й поповнюють історію, на якій навчаються моделі.

## Склад

| Складова | Що це | Де |
|---|---|---|
| GitLab CE 17.5.5 | справжній сервер неперервної інтеграції | контейнер `gitlab`, порт 8929 |
| GitLab Runner 19.4 | виконавець задач, режим `shell` | `~/gitlab-stand/runner` |
| `demo-orders` | репозиторій із 84 справжніми перевірками | `stand/demo-repo` |
| Slipstream | система оптимізації | `uvicorn app.main:app`, порт 8000 |

Демонстраційний репозиторій має власну історію комітів, тому в основному репозиторії
він зберігається як `stand/demo-repo.bundle`. Відновлення перед підняттям стенда:

```bash
git clone stand/demo-repo.bundle stand/demo-repo
```

Контейнер запускається **rootless podman**: доступу до демона Docker на машині
немає, і це виявилося несуттєвим — GitLab CE працює без нього.

## Демонстраційний репозиторій

Сервіс замовлень із чотирьох модулів. Перевірки розподілені так, щоб зв'язок
«модуль — перевірка» був змістовним, інакше відбір нема за чим робити.

| Модуль | Перевірок |
|---|---:|
| `src/auth` — маркери доступу, стійкість пароля | 23 |
| `src/billing` — рахунок, податок, знижки | 25 |
| `src/catalog` — пошук і фільтрація | 12 |
| `src/shipping` — зони доставки й тарифи | 17 |
| наскрізні — оформлення замовлення | 7 |

Історія містить 41 коміт, **з них 10 справді червоні**: дефекти внесено як
реальні зміни коду, і `pytest` на цих комітах дійсно падає. Це можна перевірити
безпосередньо, вивантаживши будь-який такий коміт і запустивши перевірки.
Зламаний стан тягнеться до коміту-виправлення, як у реальному проєкті.

## Підняття стенда

```bash
# 1. сервер неперервної інтеграції
podman run --detach --name gitlab --hostname 127.0.0.1 \
  --publish 8929:8929 --publish 2224:22 --shm-size 256m \
  --env GITLAB_ROOT_PASSWORD='<пароль адміністратора GitLab>' \
  --env GITLAB_OMNIBUS_CONFIG="external_url 'http://127.0.0.1:8929'; \
    prometheus_monitoring['enable']=false; alertmanager['enable']=false; \
    registry['enable']=false; mattermost['enable']=false; \
    gitlab_pages['enable']=false; gitlab_kas['enable']=false; \
    puma['worker_processes']=2; sidekiq['max_concurrency']=5;" \
  --volume ~/gitlab-stand/config:/etc/gitlab:Z \
  --volume ~/gitlab-stand/logs:/var/log/gitlab:Z \
  --volume ~/gitlab-stand/data:/var/opt/gitlab:Z \
  docker.io/gitlab/gitlab-ce:17.5.5-ce.0

# перше піднесення триває близько семи хвилин

# 2. проєкт, змінні, вебхук і виконавець — усе разом
./setup_stand.sh

# 3. виконавець
~/gitlab-stand/runner/gitlab-runner run --config ~/gitlab-stand/runner/config.toml

# 4. накопичення історії: кожен коміт стає гілкою й породжує конвеєр
./replay_history.sh 38
```

**Параметр `grafana` вилучати не можна забувати:** у GitLab 17 його прибрано, і
його наявність у конфігурації зупиняє контейнер на етапі `gitlab-ctl reconfigure`.

## Дві адреси, а не одна

Найпідступніше місце стенда. Задачі конвеєра виконуються **на хості** (виконавець
у режимі shell), а вебхуки надсилає **сам GitLab із контейнера**. Для контейнера
`127.0.0.1` — це він сам, тому адреса системи в цих двох випадках різна:

| Хто звертається | Адреса |
|---|---|
| задачі конвеєра (плагін, звіти JUnit) | `http://127.0.0.1:8000/api/v1` |
| GitLab (події конвеєра) | `http://172.17.0.1:8000/api/v1` |

Крім того:

* сервер має слухати не лише на `127.0.0.1` — інакше з контейнера він недосяжний
  навіть за правильною адресою;
* GitLab типово **блокує** звернення до локальної мережі з вебхуків; дозвіл
  вмикається налаштуванням `allow_local_requests_from_web_hooks_and_services`.

Якщо цього не зробити, збій буде мовчазним: звіти JUnit надходитимуть (їх шле
виконавець із хоста), а події конвеєра — ні. Назовні це виглядає як незрозуміла
відмова навчити моделі тривалості та ризику збою: у системі просто немає ні
тривалостей задач, ні різних станів прогонів. Саме так ця вада й виявилася.

`setup_stand.sh` перевіряє досяжність **до** створення вебхука й голосно
попереджає, якщо адреса недоступна.

## Що стенд виявив

Стенд не лише підтвердив роботу контуру, а й показав три вади, яких не могли
показати ні автоматичні перевірки, ні розрахунки на історичних даних.

**Опис конвеєра не був виконуваним.** Система формувала команду
`pytest --test-ids "125,97,..."` з внутрішніми ідентифікаторами перевірок.
Такого параметра в pytest немає, а ідентифікатори поза системою нічого не
означають. Тепер план несе справжні посилання виду `шлях::ім'я` і додає
формування звіту JUnit.

**Звіти не поверталися.** Задача звітування стояла в батьківському конвеєрі,
тоді як звіти утворюються в дочірньому, і дістатися до них вона не могла.
Повернення результатів вкладено в сам згенерований план.

**Система не могла почати навчатися.** У режимі холостого ходу плагін віддавав
запасний опис конвеєра, який не повертав нічого. Проєкт на початку впровадження
ніколи не накопичив би даних рівня окремої перевірки, а отже й не навчив би
моделі. Тепер повний прогін теж звітує.

**Проєкт, підключений через консоль, не отримував політик.** Їх створювали лише
сценарії імпорту історії, тому такий проєкт лишався німим: план завжди
вироджувався в повний прогін, і причина ззовні не була видна.

**Прогони не позначалися як оптимізовані.** Позначка ставилася лише з події
конвеєра, якщо той повертав особливу змінну, якої ніщо не встановлювало. Через
це показник частки оптимізованих прогонів лишався нульовим навіть у бойовому
режимі — система виглядала бездіяльною, хоча виконувала скорочений набір.
Тепер позначка ставиться в момент видачі плану.

**Згенерований план припускав, що `pytest` є у PATH.** На виконавці в режимі
shell його там немає, і задача падала з кодом 127. Для стенда додано місток на
інтерпретатор проєкту; у режимі docker це вирішується образом із залежностями.

## Межі стенда

Виконавець працює в режимі `shell`, а не `docker`: доступу до демона Docker на
машині немає. Для перевірки контуру це несуттєво — GitLab, конвеєри, дочірні
конвеєри та звіти справжні, — але ізоляції задач немає, і канонічний варіант
конфігурації з `image:` наведено окремо в `examples/.gitlab-ci.yml`.

Дефекти в історії внесено автором стенда, а не зібрано з реального розвитку
проєкту. Стенд доводить працездатність контуру; кількісні властивості методу
виміряно окремо на відкритому датасеті RTPTorrent (підрозділ 4.7.4 записки).
