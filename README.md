# Slipstream

Інформаційна система управління та оптимізації CI/CD-конвеєрів у середовищі DevOps.

Система приймає події сервера неперервної інтеграції (GitLab CI, GitHub Actions),
накопичує історію прогонів і результатів окремих перевірок, навчає прогнозні моделі
й для кожної програмної зміни формує **оптимізований план конвеєра**: пропускає
конвеєр для змін лише в документації, відбирає релевантні перевірки, розподіляє їх
між паралельними виконавцями й упорядковує задачі за ризиком. Запобіжники повертають
повний набір перевірок там, де скорочення тестування ризиковане.

## Локальний запуск

Найпростіший спосіб побачити систему в роботі: SQLite і синтетична історія проєкту.

```bash
# 1. залежності
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt

# 2. налаштування (для локального запуску значень за замовчуванням досить)
cp .env.example .env

# 3. схема бази даних
alembic upgrade head

# 4. синтетична історія: 600 прогонів за 150 днів і демонстраційні облікові записи
python scripts/seed_synthetic.py --pipelines 600 --days 150 --reset

# 5. навчання моделей для проєкту 1
python scripts/train_models.py --project 1

# 6. вебінтерфейс
cd web && npm install && npm run build && cd ..

# 7. запуск
uvicorn app.main:app --port 8000
```

Інтерфейс відкривається за адресою http://127.0.0.1:8000, документація програмного
інтерфейсу - http://127.0.0.1:8000/docs.

Генератор синтетичних даних створює три демонстраційні облікові записи:

| Роль | Адреса | Пароль |
|---|---|---|
| DevOps-інженер | `devops@example.com` | `devops123` |
| Розробник | `dev@example.com` | `dev123` |
| Керівник | `lead@example.com` | `lead123` |

Ці облікові записи призначені лише для локального стенда. На сервері створюйте
власні (див. крок 5 розгортання).

Замість синтетичних даних можна імпортувати реальну історію GitHub Actions
(маркер GitHub знімає обмеження в 60 запитів на годину):

```bash
export GITHUB_TOKEN=...
python scripts/import_github.py --repo pandas-dev/pandas \
    --workflow-file unit-tests.yml --runs 900 --skip-cancelled \
    --with-jobs 200 --with-commits 200
python scripts/train_models.py --project 2
```

## Запуск у Docker Compose

Локальний склад служб із PostgreSQL. Вебінтерфейс копіюється в образ уже зібраним,
тому його треба зібрати заздалегідь.

```bash
cd web && npm install && npm run build && cd ..
docker compose up -d --build

# дані й моделі всередині контейнера застосунку
docker compose exec api python scripts/seed_synthetic.py --pipelines 600 --days 150 --reset
docker compose exec api python scripts/train_models.py --project 1
```

Міграції застосовуються автоматично під час запуску контейнера (`alembic upgrade head`).
Застосунок доступний на порту 8000.

## Розгортання на сервері

Нижче описано розгортання, яке використано для демонстраційного стенда: одна
віртуальна машина в Microsoft Azure, на якій у Docker Compose працюють PostgreSQL,
застосунок і зворотний проксі Caddy з автоматичним сертифікатом Let's Encrypt.
На будь-якому іншому сервері з Docker порядок той самий, крім кроку 1.

### Крок 1. Віртуальна машина (Azure, Terraform)

```bash
cd deploy/azure
az login --use-device-code

cp example.tfvars terraform.tfvars
# у terraform.tfvars вказати:
#   subscription_id  - ідентифікатор підписки Azure
#   allowed_ssh_cidr - власну публічну адресу з маскою /32 (лише з неї відкрито SSH)

terraform init
terraform plan
terraform apply
```

Terraform створює групу ресурсів, мережу, групу безпеки (відкриті лише порти 22 з
вашої адреси, 80 і 443), статичну публічну адресу й віртуальну машину з Ubuntu 24.04.
Під час першого запуску машини `cloud-init.yaml` встановлює Docker, вмикає мережевий
екран `ufw`, додає файл підкачки на 2 ГБ і створює каталог `/opt/slipstream`.
Наприкінці `terraform apply` виводить адресу машини й команду підключення SSH.
Докладніше про вибір розміру машини й вартість - у [deploy/azure/README.md](deploy/azure/README.md).

### Крок 2. Доставка коду на сервер

На своїй машині зберіть вебінтерфейс і скопіюйте проєкт на сервер:

```bash
cd web && npm install && npm run build && cd ..

SERVER=azureuser@<адреса або доменне ім'я сервера>
rsync -az --exclude .venv --exclude node_modules --exclude .git \
      --exclude 'data/*.db' --exclude 'models_store/*' --exclude deploy/azure \
      ./ "$SERVER:/opt/slipstream/"
```

### Крок 3. Налаштування

На сервері створіть файл `/opt/slipstream/deploy/.env`. Таємниці згенеруйте
випадково; файл у репозиторій не потрапляє.

```bash
ssh "$SERVER"
cd /opt/slipstream/deploy
cat > .env <<EOF
POSTGRES_USER=slipstream
POSTGRES_PASSWORD=$(openssl rand -hex 24)
POSTGRES_DB=slipstream
SECRET_KEY=$(openssl rand -hex 32)
DOMAIN=slipstream.example.org
DOMAIN_LEGACY=<ім'я, видане хмарною платформою>
TRUSTED_PROXIES=1
EOF
chmod 600 .env
```

`DOMAIN` - доменне ім'я, для якого Caddy отримає сертифікат; запис DNS має вказувати
на публічну адресу машини. `DOMAIN_LEGACY` - друге ім'я, яке перенаправлятиме на
основне; воно обов'язкове й має відрізнятися від `DOMAIN`. Решту змінних наведено в
розділі [Змінні середовища](#змінні-середовища).

`SECRET_KEY` підписує маркери доступу й шифрує збережені маркери репозиторіїв.
Після розгортання його не змінюйте: інакше зашифровані значення стануть недоступними.

### Крок 4. Запуск

```bash
cd /opt/slipstream/deploy
docker compose -f docker-compose.prod.yml up -d --build
docker compose -f docker-compose.prod.yml ps
curl -fsS https://slipstream.example.org/health
```

Застосунок сам застосовує міграції під час запуску. Назовні доступні лише порти 80 і
443 через Caddy; база даних і застосунок у мережу не публікуються.

### Крок 5. Облікові записи

```bash
docker compose -f docker-compose.prod.yml exec api \
    python scripts/create_user.py --email devops@company.ua --name "Ім'я Прізвище" --role devops
```

Сценарій двічі запитує пароль (не менше 10 символів). Ролі: `devops`, `developer`,
`lead`. Для наявної адреси сценарій змінює роль і пароль. Адреса зберігається малими
літерами, і так само її треба вводити під час входу.

### Крок 6. Резервні копії й перенавчання за розкладом

```bash
sudo cp /opt/slipstream/deploy/systemd/* /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now slipstream-backup.timer slipstream-retrain.timer
systemctl list-timers 'slipstream-*'
```

Щодня о 02:30 знімається резервна копія бази (зберігаються сім останніх у
`/var/backups/slipstream`), о 03:30 - перенавчання моделей із поверненням попередньої
версії, якщо нова виявилася гіршою. Перевірити копію відновленням в окрему базу:
`./backup.sh --check`. Докладно - у [deploy/README.md](deploy/README.md).

### Оновлення розгорнутої системи

Наступні оновлення виконуються з машини адміністратора одним сценарієм:

```bash
cd web && npm run build && cd ..
./deploy/update.sh --dry-run   # які файли зміняться
./deploy/update.sh             # резервна копія, доставка коду, перескладання, перевірка
```

Сценарій спершу робить резервну копію бази, потім доставляє код і зібраний інтерфейс
(файл `.env` на сервері не чіпає), перескладає й перезапускає лише контейнер
застосунку та перевіряє, що застосунок відповідає і схема на останній ревізії.
Адреса сервера задається змінною `SLIPSTREAM_SSH` (типово
`azureuser@slipstream-ci.duckdns.org`).

### Зупинка між демонстраціями

```bash
az vm deallocate -g rg-slipstream-demo-plc -n vm-slipstream-demo-plc   # зупинити
az vm start      -g rg-slipstream-demo-plc -n vm-slipstream-demo-plc   # увімкнути
```

Після вмикання контейнери стартують самі; пропущені запуски таймерів надолужуються.

## Підключення GitLab CI

1. Увійдіть в інтерфейс як DevOps-інженер, у переліку проєктів натисніть
   **Connect a project** і вкажіть репозиторій. Система відкриє сторінку **Connect CI**:
   там натисніть **Generate secret** і скопіюйте наведений фрагмент конфігурації.
2. У налаштуваннях проєкту GitLab додайте захищену змінну `CICD_OPT_SECRET` зі
   значенням секрету та вебхук подій конвеєра на адресу, показану на сторінці.
3. Покладіть `cli/cicd_opt.py` у репозиторій (наприклад, у `ci/`) і додайте до
   `.gitlab-ci.yml` дві задачі з [examples/.gitlab-ci.yml](examples/.gitlab-ci.yml):
   `optimize` запитує план, `run-pipeline` виконує його як дочірній конвеєр.
4. Почніть з режиму **холостого ходу** (сторінка **Policies**): система рахує план, але
   конвеєр виконує повний набір, і можна порівняти прогноз із фактом. Оптимізація
   вмикається після накопичення щонайменше 60 прогонів (`MIN_PIPELINES_TO_OPTIMIZE`).

Якщо система недоступна, плагін записує запасний опис із повним набором перевірок і не
перериває конвеєр.

## Змінні середовища

| Змінна | Типове значення | Призначення |
|---|---|---|
| `DATABASE_URL` | `sqlite:///./data/cicd.db` | адреса бази даних |
| `SECRET_KEY` | - | підпис маркерів доступу й шифрування маркерів репозиторіїв; на сервері обов'язково власний |
| `MODELS_DIR` | `./models_store` | каталог файлів навчених моделей |
| `ACCESS_TOKEN_EXPIRE_MINUTES` | `480` | тривалість сеансу |
| `MIN_PIPELINES_TO_OPTIMIZE` | `60` | мінімум прогонів, після якого вмикається оптимізація |
| `DEFAULT_TEST_BUDGET_SEC` | `600` | бюджет часу на перевірки за замовчуванням |
| `TRUSTED_PROXIES` | `0` (на сервері `1`) | скільки власних зворотних проксі стоїть перед застосунком |
| `SLACK_WEBHOOK_URL`, `NOTIFY_WEBHOOK_URL` | - | канали сповіщень Slack і довільний вебхук |
| `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD`, `NOTIFY_EMAIL_FROM`, `NOTIFY_EMAIL_TO` | - | сповіщення електронною поштою |
| `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB` | - | обліковий запис PostgreSQL (лише на сервері) |
| `DOMAIN`, `DOMAIN_LEGACY` | - | доменні імена для Caddy (лише на сервері) |

Без каналів сповіщень повідомлення пишуться в журнал застосунку.

## Тестування

```bash
pytest                                  # 210 перевірок, близько півтори хвилини
pytest tests/test_safeguards.py         # запобіжники планувальника
pytest tests/test_performance.py -s     # час відповіді зі звітом
python scripts/check_ui_login.py        # вхід через справжній браузер (потрібен Chrome)
```

Перевірки працюють із локальною базою, тому перед запуском потрібні кроки 3-5
локального запуску.

## Відтворення експерименту

```bash
python scripts/run_experiment.py --project 1 --retrain
```

Сценарій перенавчає моделі лише на навчальній частині історії (перші 70 % прогонів) і
відтворює контрольні прогони так, ніби пізніших даних ще не було. Результати, наведені
в пояснювальній записці, збережено в каталозі `results/`. Щоб не змінювати робочу базу,
сценарій можна запускати на копії: `DATABASE_URL=sqlite:///копія.db MODELS_DIR=копія_моделей`.
